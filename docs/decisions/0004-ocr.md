# OCR pages without a text layer with tesseract.js

Status: accepted
Date: 25 November 2026

## Context

Fund documents arrive as scans: signed side letters, older LPAs, capital call notices printed and rescanned. The Python project's audit found that an image-only PDF was reported as "ingested OK" with zero characters, because the extractor didn't raise on empty text and the OCR fallback never ran. The rule ported here: fewer than 80% of pages with text means the extraction failed, so OCR runs; a document that still has no usable text goes to review.

The OCR step must run the same way locally, in CI and in the deployed container, and the demo has no budget for per-page API fees.

## Decision

Use [tesseract.js](https://github.com/naptha/tesseract.js) (Tesseract compiled to WebAssembly) behind an `OcrEngine` interface. Pages are rasterized at 2x scale with unpdf and `@napi-rs/canvas`. As with `ocrmypdf --skip-text`, only pages without a text layer are OCR'd, and OCR text replaces a page only when it has more letters and digits. English language data is downloaded once and cached in `.cache/tesseract` (gitignored).

## Alternatives considered

- **ocrmypdf / Tesseract CLI:** what the Python repo used. Higher throughput and a searchable PDF as output, but it needs system packages (Tesseract, Ghostscript, qpdf) in every environment. The Python audit found the fallback silently unavailable on the dev machine for exactly that reason.
- **AWS Textract / Google Document AI / Azure Document Intelligence:** much better on tables, handwriting and poor scans, and they return layout. But they cost money per page, need cloud credentials, and send documents to a third party, which is a real concern for confidential LP documents. Worth revisiting for production behind the same `OcrEngine` interface.
- **Sending page images to the LLM (vision):** good quality, but it mixes reading with interpretation. The citation check needs page text that came from the page, not from the model being validated.

## Consequences

- No system binaries: `npm ci` is enough.
- WebAssembly Tesseract is slow (about a second per page here), so OCR runs at ingestion time, never on a request path.
- The first run downloads language data from a CDN. CI does this on every fresh runner; pass `langPath` to use vendored data offline.
- `OcrEngine` is injected, so ingestion tests use a fake engine for the routing logic, plus one test that runs real Tesseract on an image-only PDF.
- Tesseract's quality on poor scans is limited. Its output goes through the same quality score, and `poor` sends the document to review instead of letting bad text into extraction.
